## 초기 사용량에도 발생하는 서버 고정비와 운영 부담

듀티라운지는 카지노 교대 근무자가 개인 일정을 관리하고 그룹으로 공유하는 앱입니다. Cafe24에서 NestJS·Prisma·MySQL과 자체 JWT 인증을 운영했는데, 초기 사용량에도 월 11,000원의 고정비와 OS·API·DB 관리가 필요했습니다.

직접 운영할 범위를 줄이기 위해 관계형 데이터와 인증을 함께 제공하는 Supabase를 선택했습니다. DB 이전과 함께 앱 호출·인증·사용자별 접근 권한을 새 구조에 맞춰 전환해야 했습니다.

## 데이터·인증 이전과 접근 권한 문제 해결

MySQL 데이터를 PostgreSQL로 변환하고, 자체 인증을 Supabase Auth로 바꾸면서 사용자 참조를 Auth·profiles의 UUID에 맞췄습니다. 이전 과정에서 자료형 변환 누락으로 import가 실패하고, RLS 적용 후 일정·그룹 조회가 막히는 문제를 겪었습니다.

변환 처리를 보완하고 **데이터 소유자·그룹 가입 관계에 따른 RLS 정책과 권한 확인을 포함한 RPC**를 구성했습니다. 2025년 Supabase Free Plan으로 이전한 당시 서버 고정비는 **월 11,000원 → 0원**으로 줄었습니다.

## 그룹 일정은 멤버별 요청 대신 일괄 조회

이전 이후의 앱 개선에서는 그룹의 월별 조회 구조를 점검했습니다. 멤버 목록을 읽고 각 멤버의 일정·근무를 따로 요청해, N명 기준 데이터 조회가 **1 + 2N회**로 늘어났습니다. 병렬 실행만으로는 요청 수가 줄지 않아 조회 단위를 바꿨습니다.

멤버 ID로 일정·근무를 일괄 조회해 Map으로 조합하고, URL 길이·반환 행 제한에 맞춰 50명 청크·100행 페이지 처리를 적용했습니다. **50명·단일 페이지 모의 데이터에서 101회 → 3회**를 확인했습니다. 인증·그룹·가입 확인 3회는 별도이며, 데이터가 많으면 청크·페이지 요청이 늘어납니다.

## 저장 결과와 미저장 편집을 오래된 조회로부터 보호

일정 편집 화면은 조회 결과와 저장 응답을 같은 캐시에 반영합니다. 단일 저장 재현 실험에서 **저장 응답 뒤에 이전 조회가 늦게 도착하면 새 값이 옛 값으로 덮이는 문제**를 확인했습니다.

이전 조회를 취소한 뒤 저장 응답을 반영하고, 계정이 바뀌면 이전 계정의 응답을 제외하도록 했습니다. 편집 초안도 서버 응답과 분리해 재조회로 초기화되지 않도록 구성했습니다. 느린 조회·계정 전환·초안 보존을 회귀 테스트로 확인했습니다.
