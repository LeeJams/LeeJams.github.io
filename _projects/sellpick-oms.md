## 주문 목록에서 페이지를 넘길수록 늘어나는 조회 시간

OMS의 주문 목록은 여러 판매 채널의 주문을 확인하고 배송·취소·반품 업무를 시작하는 화면입니다. 데이터가 많은 환경에서 **같은 검색 조건·정렬·페이지 크기로 조회해도 1페이지는 약 20초, 10페이지는 약 100초**가 걸렸습니다.

페이지를 넘길수록 건너뛸 행 수(OFFSET)가 늘어나는 점에 주목해 쿼리와 `EXPLAIN (ANALYZE, BUFFERS)` 실행 계획을 확인했습니다. 상품·재고·금액·상태를 계산하는 노드의 **반복 횟수(loops)가 페이지 크기보다 훨씬 많았습니다.** 이 쿼리는 현재 페이지에서 반환하지 않을 주문에도 상세 계산을 한 뒤, 앞 페이지의 결과를 OFFSET으로 버리는 구조였습니다.

현재 페이지에 들어갈 주문의 식별 키(PK)를 먼저 고르고, 선택된 주문에만 상세 정보를 붙이는 **2단계 페이징**으로 바꿨습니다. OFFSET의 키 탐색은 남기되 비용이 큰 상세 계산의 범위를 줄였고, 실행 계획에서도 해당 노드의 반복 범위가 줄었는지 확인했습니다.

## 조회 구조를 바꾸면서 기존 검색·정렬 결과 유지

성능을 개선해도 주문 목록이 반환하는 값과 순서는 같아야 했습니다. PK 선별과 상세 조회를 나누면서 두 단계의 검색·정렬 조건이 달라지거나, 정렬값이 같은 주문의 순서가 흔들리지 않는지 확인했습니다.

동적 정렬 조건을 같은 SQL 조각으로 공유하고 PK를 보조 정렬 기준으로 추가했습니다. 복합 PK 연결을 맞춘 뒤 **변경 전후의 건수·PK 순서·반환 컬럼을 대조**해 조회 결과의 동등성을 검증했습니다.

## 여러 판매 채널의 주문 수집이 겹칠 때 실행 제어

주문 목록에 표시할 데이터는 여러 판매 채널의 수집 작업을 통해 들어옵니다. 수집 작업이 겹치는 상황에서는 같은 주문이 중복 처리되지 않도록 동시 실행을 제어해야 했습니다.

Redis 분산 락을 적용해 중복 수집을 제어했습니다. 수집 실패와 쇼핑몰 API 변경은 운영 이슈로 추적하고, Grafana·OpenLens로 지표와 파드·배포 상태를 확인했습니다.
