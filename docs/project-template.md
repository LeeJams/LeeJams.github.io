## 배경과 해결할 문제

대상 사용자와 업무·기능의 용도를 먼저 설명하고, 실제로 관찰한 현상과 조건으로 이어갑니다. '뒤 페이지', '이전 값', '원본' 같은 표현은 무엇을 가리키는지 앞에서 밝혀야 합니다. 신규 기능이라면 실제 장애처럼 쓰지 않고 요구 조건과 예방할 위험을 설명합니다.

## 해결 전략과 판단 근거

코드·실행 계획·재현 결과에서 확인한 근거와 선택한 방식을 연결합니다. 어떤 조건 때문에 이 방식을 선택했는지, 구현에서 책임과 범위를 어떻게 나눴는지 적습니다. 상단에 성과가 있어도 원인을 이해하는 데 필요한 맥락은 생략하지 않습니다.

실제 시행착오가 있으면 관련 해결 과정 안에서 발견한 현상·규칙 보완·재확인을 설명합니다. 다른 기능의 이야기라면 그 기능의 맥락부터 소개합니다. 관찰하지 않은 장애나 분석 과정은 만들지 않습니다.

## 검증과 결과

변경한 동작을 무엇으로 확인했는지 적습니다. 수치는 측정 시점·범위·조건을 포함하고, 구현한 기능이나 공개한 산출물도 결과로 설명할 수 있습니다. 모의 테스트와 운영 측정, 정책 범위 변경과 코드 개선의 효과를 구분합니다.

위 순서는 작성 기준입니다. 실제 제목은 프로젝트의 핵심 내용을 드러내도록 바꾸고, 짧은 글은 검증 결과를 해당 해결 과정에 묶어도 됩니다. 짧게 쓰되 논리의 연결을 없애지 않으며, 기능 나열·자기소개·반복되는 결론은 생략합니다. 관련 블로그 글은 본문 뒤의 관련 문서에서 연결합니다.
